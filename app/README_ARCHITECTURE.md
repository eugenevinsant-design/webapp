# Архитектура ECG Analyzer (Backend)

Этот документ описывает ключевые архитектурные решения, принятые при рефакторинге бэкенда для сервиса-аннотатора ЭКГ.

## 1. Контракт данных (prompt-словарь)

Единый формат для всех режимов:

- question: str
- raw: np.ndarray (None в режиме 2)
- fs: float (None в режиме 2)
- grade: int (0-10)
- context: str

## 2. Почему ContextVar, а не обычная глобальная переменная

ТЗ требует глобальную переменную prompt, но в асинхронном FastAPI обычная глобальная переменная вызывает Race Condition. Используем contextvars.ContextVar — изолирует состояние для каждой сессии.

## 3. Почему нейросеть заменена заглушкой

Реальная модель не подключена. Mock в app/core/nn_pipeline.py имитирует генерацию. Контракт (вход: prompt-словарь, выход: context) уже зафиксирован. При замене нужно менять только внутренности nn_pipeline.py.

## 4. Почему добавлен слой БД

ТЗ требует сохранять prompt в БД. Добавлены модели User, Session, PromptState. Вместо raw хранится file_path (путь к файлу), так как ndarray нельзя сохранить в реляционную БД.

## 5. Resolve-модуль

app/core/resolver.py парсит команды вида \choose_pkg. Спроектирован расширяемым через словарь COMMANDS.

## 6. Соединение с UI

- GET /api/ecg/packages — список доступных пакетов для выбора.
- POST /api/chat — принимает текст, обрабатывает через resolver, вызывает nn_pipeline, возвращает context.

## 7. Структура проекта

- app/main.py — точка входа FastAPI, ContextVar, middleware
- app/database.py — подключение к БД
- app/models_db.py — SQLAlchemy-модели
- app/api/routes/chat.py — новый роут для чата
- app/core/nn_pipeline.py — заглушка нейросети
- app/core/resolver.py — Resolve-модуль

## 8. current_raw_pkg и его связь с raw в prompt

В ТЗ многократно упоминается `current_raw_pkg` — это локальное поле, которое обновляется при выборе пакета. В нашем контракте `prompt` поля `raw` и `fs` заполняются не всегда:

- **Режим 1 (выбор + вопрос):** `raw` и `fs` заполняются (через wfdb), `question` — комментарий.
- **Режим 2 (только выбор):** `raw` и `fs` = None (в контракте), но выбор фиксируется в сессии.
- **Режим 3 (обычный вопрос):** `raw` и `fs` берутся из `current_raw_pkg` (сохраненного в БД), `question` — текст вопроса.
- **Режим 4 (оценка + перегенерация):** `raw` и `fs` не меняются, `grade` и `context` — единственные меняющиеся поля.

**Решение:** В БД (`PromptState`) храним `current_raw_pkg_path` — путь к файлу внутри локального хранилища. В `prompt`-словаре `raw` заполняется только когда это необходимо (режимы 1, 3, 4). В режиме 2 `raw = None`, но `current_raw_pkg_path` в БД обновлен.

## 9. Режим 4: оценка и перегенерация

ТЗ требует: сначала оценка (0-10), затем предложение перегенерировать. Единственные меняющиеся поля — `grade` и `context`.

**Что происходит с prompt при перегенерации (дописываем оборванное предложение из ТЗ):**
- `question` и `raw`/`fs` **не меняются** (используем те же данные, что и в предыдущей генерации).
- `context` **обновляется** (новый ответ модели).
- `grade` **сбрасывается в None** (пользователь должен оценить новый ответ заново).

**Роуты:**
- `POST /api/chat/grade` — принимает `grade` (0-10), обновляет только это поле в БД.
- `POST /api/chat/regenerate` — вызывает `nn_pipeline` заново с тем же `question` и `raw`, обновляет `context`, сбрасывает `grade`.

## 10. Атомарность обновления prompt

ТЗ: "ни одно из полей prompt не меняется до тех пор, пока промт не будет составлен корректно".

**Решение:** При обработке запроса работаем с копией `prompt` из `ContextVar`. Изменения применяем только после успешной валидации (например, файл для `\choose_pkg` существует). Если файл не найден — возвращаем список доступных файлов, не трогая текущий `prompt` ни в памяти, ни в БД.

## 11. Что делать при подключении реальной нейросети

1. Открыть app/core/nn_pipeline.py.
2. Заменить внутренности generate_response(prompt: dict) -> str.
3. Не менять контракт prompt.

*При изменении архитектуры — обновляйте этот файл.*
